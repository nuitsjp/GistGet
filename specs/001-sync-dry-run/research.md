# 調査: sync dry-run

## 決定 1: dry-run は既存の `sync` 経路にフラグとして追加する

**決定**: `sync` コマンドに `--dry-run` を追加し、`IGistGetService.SyncAsync` に dry-run 指定を渡す。

**理由**: ユーザーにとって dry-run は通常同期の実行前確認であり、別コマンドにすると `--url` や `--file` との関係が分かりにくくなる。既存の同期元読み込み経路を再利用でき、対象範囲も最小になる。

**検討した代替案**: `sync preview` のようなサブコマンドを追加する案。既存の `sync` オプションと重複し、ユーザー操作とテスト範囲が増えるため採用しない。

## 決定 2: dry-run は状態取得だけを許可し、実操作と保存を禁止する

**決定**: dry-run では同期元読み込み、ローカル導入済みパッケージ取得、ピン状態取得だけを許可する。インストール、アンインストール、アップグレード、ピン変更、Gist 保存は実行しない。

**理由**: 仕様の中心価値は「実行前に影響を確認すること」であり、プレビューが外部状態を変えると信頼できない。憲章の破壊的操作分離にも合致する。

**検討した代替案**: 実操作直前まで進めてコマンド文字列だけを表示する案。既存処理の副作用境界が曖昧になり、誤実行のリスクがあるため採用しない。

## 決定 3: 結果は `SyncResult` を最小拡張して返す

**決定**: dry-run 専用メソッドは追加せず、`SyncResult` にアップグレード予定、更新不要件数、dry-run 判定に必要な最小項目を追加する。

**理由**: 既存の `sync` 表示は `CommandBuilder` が `SyncResult` を見て行っている。戻り値を分けるより、既存の責務を保ったまま dry-run 表示に必要な情報を足す方が単純。

**検討した代替案**: `DryRunResult` を新設する案。同期結果とプレビュー結果の二重管理になり、現時点では重複が増えるため採用しない。

## 決定 4: 表示は CLI 層で表形式にする

**決定**: dry-run の一覧表示は `CommandBuilder` 側で行い、操作種別ごとの件数と対象を表で表示する。

**理由**: 既存の通常同期も CLI 層で結果表示しているため、サービス層に表示責務を増やさずに済む。ユーザーは操作種別を見て実行判断できる。

**検討した代替案**: サービス層で文字列を組み立てる案。表示と同期判定が混ざるため採用しない。

## 決定 5: TDD は UI 契約からサービス副作用禁止へ進める

**決定**: 最初に `sync --dry-run` がサービスへ dry-run 指定を渡す失敗テストを書く。次にサービス側で副作用禁止と分類結果を失敗テストで固定し、最後に表示の失敗テストを追加する。

**理由**: ユーザー入口、実操作禁止、分類表示の順にリスクが高く、RED-GREEN-REFACTOR の単位を小さく保てる。

**検討した代替案**: サービス分類ロジックを先にまとめて実装する案。複数の RED を溜めやすくなるため採用しない。
